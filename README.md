# Mini NPU Simulator — 3차 미션

파이썬으로 인공지능 가속기(NPU)의 핵심 연산 원리를 이해하고 구현하는 학습용 프로젝트입니다.
함수와 클래스 설계, 행렬 기반 MAC 연산, Bias 추가, ReLU 활성화 함수, JSON 데이터 관리를 연습합니다.
3차 미션에서는 사용자 입력 및 JSON 패턴의 필터별 MAC 점수 비교, 정답 판정, 실행 시간 측정을 수행합니다.

## 실행 환경

- Python 3을 사용하며, 확인한 환경은 Python 3.10.12입니다.
- `json`, `math`, `pathlib`, `re`, `time.perf_counter` 등 Python 표준 라이브러리만 사용합니다.
- 외부 패키지를 설치할 필요가 없으며 배열은 중첩 리스트로 표현합니다.

## 파일 구성

```text
mini_npu_sim/
├── main.py
├── data.json
└── README.md
```

| 파일 | 역할 |
|---|---|
| `main.py` | MAC 계산, 점수 비교, 입력 검증, 라벨 정규화, JSON 분석, 성능 측정, MiniNPU 클래스 및 메뉴 |
| `data.json` | 크기별 필터와 정답이 포함된 패턴 6개 |
| `README.md` | 실행 안내, 데이터 구조, 테스트 결과 및 결과 분석 |

## 실행 방법

프로젝트 폴더에서 실행합니다.

```bash
python3 main.py
```

시작 시 기존 MiniNPU 예제가 `NPU 최종 연산 결과: 3.0`을 출력한 뒤 메뉴를 표시합니다.

```text
1. 필터 A, 필터 B, 패턴 입력
2. data.json 분석
0. 종료
```

분석이 끝나면 메뉴로 돌아오며 `0`으로 종료합니다.
JSON은 현재 작업 폴더가 아니라 `main.py`가 위치한 폴더를 기준으로 읽습니다.

### 모드 1: 3×3 사용자 입력

`1`을 선택하고 필터 A, 필터 B, 패턴 순서로 각각 세 행을 입력합니다.
각 행에는 공백으로 구분한 숫자 세 개를 입력하며 정수·음수·실수를 사용할 수 있습니다.
열 개수가 다르거나 숫자로 변환할 수 없는 문자가 있으면 안내 후 해당 행만 다시 입력받습니다.

예를 들어 십자가 배열은 다음과 같이 입력합니다.

```text
0 1 0
1 1 1
0 1 0
```

입력 완료 후 세 배열, A 점수, B 점수, 최종 판정(`A`, `B`, `UNDECIDED`)을 출력합니다.
이어 코드에 준비된 고정 3×3 십자가 테스트 패턴과 십자가 필터로 성능을 측정합니다.
이 성능 측정에는 사용자가 입력한 배열 대신 테스트 배열을 사용합니다.

### 모드 2: JSON 자동 분석

`2`를 선택하면 `data.json`을 읽고 구조와 배열을 검증합니다.
검증된 각 패턴에 같은 크기의 `cross`, `x` 필터를 적용하고 케이스 ID·두 점수·예측·정답·PASS/FAIL을 출력합니다.
예측과 정규화된 정답이 같으면 PASS이며, 다르거나 특정 정답에 대해 `UNDECIDED`이면 FAIL입니다.
검증 오류, 정답 누락, 잘못된 정답 라벨도 해당 케이스의 FAIL 사유로 기록하고 나머지 케이스를 계속 분석합니다.
마지막에는 전체·PASS·FAIL 수와 실패 ID 및 사유, 크기별 성능 표를 출력합니다.
JSON 읽기에 실패하면 오류를 안내하고 메뉴로 돌아옵니다.

## MAC 연산과 epsilon 판정

`calculate_mac(pattern, filter_weights)`는 같은 위치의 두 값을 곱해 모두 더합니다.

```text
MAC = Σᵢ Σⱼ pattern[i][j] × filter_weights[i][j]
```

외부 배열 라이브러리 없이 이중 `for`문으로 구현하며 행·열 크기가 맞지 않으면 `ValueError`를 발생시킵니다.
N×N 배열의 함수 호출 1회는 N²개 위치의 곱셈·누적을 수행합니다.
독립 MAC 함수는 곱셈·누적 값을 반환하며 기존 `MiniNPU.run()`은 MAC → Bias → ReLU 순서로 동작합니다.

`compare_scores(score_a, score_b, epsilon=1e-9)`의 기준은 다음과 같습니다.

| 조건 | 반환값 |
|---|---|
| `abs(score_a - score_b) < epsilon` | `UNDECIDED` |
| 동점 조건에 해당하지 않고 A 점수가 더 큼 | `A` |
| 동점 조건에 해당하지 않고 B 점수가 더 큼 | `B` |

차이가 정확히 epsilon인 경우는 동점 조건에 포함되지 않습니다.
모드 2에서는 A를 `Cross`, B를 `X`로 변환하며 `UNDECIDED`는 유지합니다.

## JSON 구조와 라벨 정규화

| 경로 | 형식 및 내용 |
|---|---|
| `meta` | 객체. `version`은 `"1.0"`, `type`은 `"json"` 문자열 |
| `filters` | 객체. 크기 키는 `size_5`, `size_13`, `size_25` |
| `filters.size_N` | `cross`, `x` 필터를 담은 객체. 각각 N×N 숫자 배열 |
| `patterns` | `size_N_idx`를 케이스 ID로 사용하는 객체 |
| `patterns.size_N_idx.input` | N×N 숫자 배열 |
| `patterns.size_N_idx.expected` | 정답 문자열. 실제 데이터는 `"+"` 또는 `"x"` |

각 크기에는 패턴이 2개씩 있어 전체 6개입니다.
크기는 별도의 `size` 필드 대신 키와 배열에서 확인하며 `idx`는 양의 정수입니다.
검증 시 필수 키, 객체 형식, 지원하는 크기, 모든 행·열 길이, 숫자 형식을 확인합니다.
JSON 배열 값은 유한한 정수 또는 실수여야 하며 문자열·불리언·비유한 실수는 허용하지 않습니다.

`normalize_label()`은 앞뒤 공백을 제거하고 아래와 같이 변환합니다.

| 입력 라벨 | 표준 라벨 |
|---|---|
| `cross`, `Cross`, `+` | `Cross` |
| `x`, `X` | `X` |

알 수 없는 라벨이나 문자열이 아닌 값에는 `ValueError`를 발생시킵니다.
모드 2에서는 `expected`를 이 함수로 정규화하며 필터는 원래 키 `cross`, `x`로 조회합니다.

## 실제 테스트 결과

실제 JSON 데이터는 구조 검증에서 정상 6개, 오류 0개였습니다.
자동 판정 결과는 **전체 6개, PASS 3개, FAIL 3개**입니다.
아래 점수는 가독성을 위해 반올림한 값이며 실제 판정에는 반올림 전 값과 epsilon을 사용합니다.

| 케이스 ID | Cross 점수 | X 점수 | 예측 | 정규화된 정답 | 결과 |
|---|---:|---:|---|---|---|
| `size_5_1` | 0.9 | 약 0.9 | UNDECIDED | X | FAIL |
| `size_5_2` | 8.9 | 0.1 | Cross | Cross | PASS |
| `size_13_1` | 0.3 | 약 14.7 | X | X | PASS |
| `size_13_2` | 약 7.5 | 7.5 | UNDECIDED | Cross | FAIL |
| `size_25_1` | 4.9 | 약 4.9 | UNDECIDED | X | FAIL |
| `size_25_2` | 52.9 | 0.1 | Cross | Cross | PASS |

실패한 `size_5_1`, `size_13_2`, `size_25_1`은 모두 epsilon 동점으로 예측이 `UNDECIDED`가 되어 특정 정답과 일치하지 않은 케이스입니다.

추가로 확인한 테스트는 다음과 같습니다.

- 3×3 십자가 패턴은 십자가 필터에서 5, X 필터에서 1을 반환했습니다.
- A 승리, B 승리, epsilon 동점 및 epsilon 경계값 판정이 기대 결과와 일치했습니다.
- 실제 `expected` 6개는 `Cross` 3개와 `X` 3개로 정규화되었고 크기별 필터 라벨도 정상 변환되었습니다.
- 사용자 입력의 문자·열 개수 오류 후 해당 행 재입력을 확인했습니다.
- 임시 데이터의 크기 불일치, 필터 누락, 정답 누락 및 잘못된 라벨을 검출하고 후속 케이스 분석을 계속했습니다.
- 기존 MiniNPU 예제의 결과 3.0과 다른 작업 폴더에서의 JSON 로드를 확인했습니다.

## 성능 측정 결과

`time.perf_counter()`로 기존 `calculate_mac()` 호출 전후를 측정하고 각 크기에서 100회 평균을 구했습니다.
평균 시간(ms)은 `누적 경과 시간(초) / 반복 횟수 × 1000`으로 계산하며 소수점 9자리로 출력합니다.
파일 읽기, JSON 데이터 검증, 배열 준비, 화면 출력은 측정 구간에서 제외합니다.
다만 기존 `calculate_mac()` 내부의 행·열 크기 확인은 함수 호출 시간에 포함됩니다.

| 배열 크기 | MAC 연산 횟수(N²), 호출 1회 기준 | 반복 횟수 | 평균 실행 시간(ms) |
|---|---:|---:|---:|
| 3×3 | 9 | 100 | 0.001541520 |
| 5×5 | 25 | 100 | 0.003066230 |
| 13×13 | 169 | 100 | 0.009784990 |
| 25×25 | 625 | 100 | 0.043508680 |

위 값은 제공된 실제 측정 기록입니다.
3×3은 고정 십자가 테스트 배열을 사용했습니다.
나머지는 각 크기의 첫 구조 검증 정상 패턴(`size_5_1`, `size_13_1`, `size_25_1`)과 해당 Cross 필터를 사용했습니다.
PASS/FAIL과 구조 검증 정상 여부는 별개이므로 동점 FAIL 패턴도 성능 측정에 사용할 수 있습니다.
해당 크기에 검증된 패턴과 필터가 없으면 그 크기의 측정을 생략합니다.

## 결과 리포트

### 데이터 구조 및 형식

1. 실제 `data.json`의 6개 패턴은 대응하는 두 필터와 행·열 크기가 모두 일치했습니다.
2. 실제 배열에서 비숫자 값이나 불규칙한 행은 발견되지 않았으므로 이번 FAIL의 원인은 데이터 구조나 형식 오류가 아닙니다.
3. 정답의 `+`와 필터 키 `cross`는 표기가 다르지만 정답 정규화와 예측 라벨 변환으로 같은 `Cross` 이름을 사용합니다.

### 프로그램 로직

4. 확인한 테스트 범위에서 MAC 계산, 높은 점수 선택, epsilon 동점 처리 및 정답 비교는 명시된 규칙과 일치했습니다.
5. 기존 MiniNPU 예제도 3.0을 유지했으므로 이번 결과에서 기존 예제의 동작 변경은 확인되지 않았습니다.
6. 임시 오류 데이터에서도 사유를 기록하고 다음 케이스를 검사했으며 자동 분석이 중간에 중단되지 않는 것을 확인했습니다.

### epsilon 동점으로 발생한 FAIL

7. `size_5_1`의 두 점수는 약 0.9로 같고 실제 부동소수점 차이는 약 1.11×10⁻¹⁶이므로 동점입니다.
8. `size_13_2`의 두 점수는 약 7.5이며 차이 약 2.66×10⁻¹⁵가 epsilon보다 작아 동점입니다.
9. `size_25_1`의 두 점수는 약 4.9이며 차이 약 1.78×10⁻¹⁵가 epsilon보다 작아 동점입니다.
10. 세 케이스는 특정 정답이 있어도 예측이 `UNDECIDED`이므로 규칙에 따라 FAIL이며 이 결과만으로 프로그램 로직 오류라고 볼 수는 없습니다.
11. epsilon은 표현 오차 수준의 차이를 승패로 해석하지 않게 하며 현재 필터 점수만으로 구분되지 않는 패턴을 동점으로 남깁니다.

### 배열 크기와 실행 시간

12. 측정된 평균 시간은 3×3의 0.001541520 ms에서 25×25의 0.043508680 ms로 배열 크기와 함께 증가했습니다.
13. 이중 반복문이 N개 행과 N개 열을 모두 방문하므로 MAC 계산의 시간 복잡도는 O(N²)입니다.
14. O(N²)는 한 변의 길이가 두 배일 때 처리하는 위치 수가 약 네 배가 된다는 뜻이며 실제 시간이 항상 정확히 네 배라는 뜻은 아닙니다.
15. 함수 호출, 내부 크기 검사, 타이머 비용과 실행 중 변동의 영향으로 측정 시간이 N²에 정확히 비례하지 않을 수 있습니다.
16. CPU 성능, 운영체제 스케줄링, Python 버전 및 시스템 부하에 따라 실행 시간이 달라지므로 이 표는 해당 측정 기록으로 해석해야 합니다.
